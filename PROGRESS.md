# ArchViz Map - build log & handoff doc

**What we are building:** a lightweight web version of our Unreal archviz product. A
Google/Apple-Maps-style 3D map where every client's project sits at its real location,
its 3D model streams in only when you fly near it, and clicking it opens project
details, amenities and a link into the full Unreal experience.

**Why:** the Unreal build is one heavy app per builder. This is one web service that
carries *all* clients, loads nothing until it is needed, and runs on a phone.

**Status:** prototype working end to end (2026-08-28). See README.md for how to run it
and how to add a client.
**Run it:** `cd archviz-map && node serve.mjs` then open http://localhost:5173

---

## Architecture in one paragraph

MapLibre GL JS draws the basemap (Carto vector tiles for day/night, Esri raster for
satellite - no API keys needed). A three.js custom layer shares MapLibre's WebGL
context and draws project geometry in the same camera, so 3D models sit correctly in
the map with real perspective. A streaming manager watches the viewport and promotes
or demotes each project through an LOD ladder. Project data lives in
`data/projects.json`, generated by `tools/gen-projects.mjs` - that file is the stand-in
for a CMS, and adding a client is a data edit, not a code change.

### The LOD ladder (the "how do we optimise" answer)

| Tier | Zoom | What renders | Cost |
|---|---|---|---|
| PIN | < 12.5 | clustered dots from the registry | a few KB total |
| MASSING | 12.5 - 14.6 | tower footprints extruded by the GPU from registry numbers | no asset fetch at all |
| MODEL | > 14.6, in viewport | full geometry, nearest 4 projects | only for what's on screen |
| DETAIL | > 16.0, selected | amenity hotspots, shadows | one project at a time |

Models are evicted by an LRU with a memory budget, and the HUD shows resident count /
queue / KB so the streaming behaviour is visible in a demo.

### Verified working in Chrome

- Cold load, 10 projects clustered across India, sidebar + filters + search.
- Selecting a project: camera flight, massing tier during load, then full geometry.
- LOD ladder measured directly: Mumbai 1 model resident -> fly to Bengaluru, Mumbai
  evicted and 3 loaded -> fly to Gurugram, those evicted -> zoom out, 0 resident.
- Deep link `?p=<id>` selects and flies to a project on load.
- Day -> Night style switch keeps the 3D models and relights them.

### Fixed during the smoke test

1. App opened off MapLibre's `load` event, which can stay pending while tiles trickle
   in - now opens on `style.load` with a timeout failsafe.
2. Lighting was blowing out facades (then too dark) - palette and light rig retuned.
3. A style switch drops our sources/layers, and MapLibre silently ignores `addLayer`
   (no throw) until the new style reports loaded. `installLayers` now attempts the
   install, checks whether it actually took, and retries on a timer. An earlier
   version retried on the map's `idle` event, which never fires in a background tab -
   don't go back to that.
4. Amenity labels collided on small sites - now icon-first, name reveals on hover.

Note for whoever tests next: Chrome stops firing animation frames in a background or
occluded tab, so `flyTo` freezes, `map.loaded()` stays false and screenshots time out.
That is the browser, not the app. Use `window.__app.map.jumpTo(...)` plus
`window.__app.streaming.update()` to exercise the logic without a visible window.

## Round 2 (2026-08-29) - bug fixes + globe

- [x] 12. **City filters would not scroll.** The chip rail overflows horizontally but a
      mouse wheel only reports vertical delta, so it looked stuck. Now wheel-scrolls,
      drags with the pointer, fades whichever edge has more chips behind it, and
      scrolls the active chip into view. A drag that ends on a chip no longer selects
      that city. Note: wheel scrolling sets `scrollLeft` directly - do NOT put
      `scroll-behavior: smooth` back on `.filters`, it defers the move to an animation
      frame and feels broken.
- [x] 13. **Amenity icons replayed their pop-in animation.** Clicking an amenity flies
      the camera, `moveend` fired `syncAmenities`, and that tore every marker down and
      rebuilt it. `showAmenities` is now idempotent - same project, same DOM nodes -
      and only rebuilds when the project actually changes.
- [x] 14. **Buildings disappearing.** Root cause: visibility was tested against
      `map.getBounds()`, which stops describing what you can see once the camera is
      pitched - so a project you were looking at could fall outside the box and have
      its geometry evicted mid-look. Now tested in screen space (with globe occlusion),
      plus zoom hysteresis so a small wheel nudge below the promotion zoom does not
      throw the model away. Also hardened the renderer: during a style swap the old
      custom layer's `onRemove` could dispose the *new* renderer and leave nothing
      drawing - each layer now only tears down the renderer it owns.
- [x] 15. **Globe.** Upgraded MapLibre 4.7 -> 5 (`@5`, currently 5.24) and turned on
      globe projection, with a globe/flat toggle in the map tools. MapLibre eases into
      flat mercator by itself as you zoom in, so the close-up view is unchanged.
      This required reworking how models are placed: instead of one shared mercator
      anchor, each project now renders in its own local frame from
      `transform.getMatrixForModel(lngLat, 0)`, one pass per resident model. That is
      what makes geometry sit correctly on a curved globe, and it also deleted the old
      float32 precision workaround. There is still a mercator fallback path if
      `getMatrixForModel` is missing.

- [x] 16. **Models were tipped over / rotated wrong** (regression from step 15, spotted
      by Naman in a zoomed-in screenshot: buildings lying on their side and the site
      plate rotated away from the GeoJSON site polygon under it).
      I had assumed MapLibre's model frame was Z-up and applied a `rotateX(90deg)`
      flip. It is not. Measured it in the browser by comparing the matrix columns of
      `getMatrixForModel` against the translations of matrices sampled 1000 m east,
      1000 m north and 1000 m up:

      | model axis | east | north | up |
      |---|---|---|---|
      | X | 1 | 0 | 0 |
      | Y | 0 | 0 | 1 |
      | Z | 0 | -1 | 0 |

      So the frame is metres in the **glTF convention - X east, Y up, Z south** -
      which is exactly how our geometry is already built. The flip is gone from that
      path. `FLIP` still exists but is now used *only* by the mercator fallback, which
      genuinely does land in a Z-up world space. **Do not add a flip back to the
      `getMatrixForModel` path.**
      Checked analytically afterwards: the three.js site corner and the GeoJSON site
      polygon corner agree to 0 m.

Verified after round 2: globe renders with clustered pins (10/10 in view), flying to a
project still streams geometry (2 resident), shadows clearly visible, buildings upright
and aligned to the map, filter rail scrolls both ways, amenity markers keep their DOM
nodes across repeat calls.

Worth knowing for future rounds: a wrong orientation is hard to spot on a big flat
township at a distance - it reads as "slightly odd perspective". Check a small site
with tall towers (Digi Quarter, Bhooja One) where lying-down buildings are obvious, and
compare the three.js ground plate against the translucent `site-fill` polygon, which is
drawn straight from the registry and is therefore the ground truth.

## Round 3 (2026-08-29) - real assets, LODs, mesh optimisation

Naman asked: if he sends a lat/lng and a model, can we place it properly - and can we
generate a low-poly LOD and optimise the high-poly mesh.

- [x] 17. **Placement from data.** `plan.asset` now takes `scale` (units -> metres),
      `heading` (degrees clockwise from north), `offset` (metres east/up/south) and
      `autoGround` (drops the model so its lowest point rests on the ground). The
      loader also measures the model footprint and warns in the console with the exact
      `scale` to set when it looks like a unit mismatch, because that is the failure
      that wastes the most time.
- [x] 18. **Compressed-mesh decoders.** DRACOLoader + MeshoptDecoder wired into
      GLTFLoader, so the files the pipeline emits actually load.
- [x] 19. **`tools/prepare-model.mjs`** - one client export in, `high/mid/low` .glb out,
      plus the registry block printed ready to paste. Cleanup (dedup, flatten, join,
      weld, prune) then Draco; mid/low additionally simplified with meshoptimizer and
      their textures resized. `npm install` needed (deps are dev-only; the app itself
      still has zero runtime dependencies and loads from CDN).
- [x] 20. **`tools/make-sample-glb.mjs`** - generates a throwaway export so the pipeline
      can be tested without a client asset.
- [x] 21. **Runtime LOD ladder for assets.** `LOD.assetLevels` maps zoom to level
      (low 14.6 / mid 15.6 / high 16.4). The streaming manager tracks which build is
      resident, swaps when the level changes, and only frees the old build once the new
      one has loaded so there is never an empty frame. Procedural projects mirror the
      same ladder in geometry detail (`DETAIL` in buildings.js), so the swap is
      demonstrable before any real geometry exists. HUD shows the level next to the tier.

Measured end to end, not assumed:

| Level | Size | Triangles | Draw calls |
|---|---|---|---|
| source | 442 KB | 18,480 | 5 |
| high | 27 KB | 18,480 | 1 |
| mid | 16 KB | 6,468 | 1 |
| low | 5 KB | 1,477 | 1 |

Then loaded those real Draco files in the browser against a project's lat/lng: placed
correctly, upright, grounded, and the level swapped low -> mid -> high as the camera
came in (44 KB -> 187 KB -> 478 KB of resident geometry).

## Decisions made

- **MapLibre, not Cesium/Google Photorealistic Tiles.** No API key, no per-load billing,
  and the vector basemap look is closer to Apple Maps. Cesium + 3D Tiles is the right
  upgrade later if we need terrain and real city meshes.
- **Procedural buildings for the prototype.** The registry has a `plan` spec so the demo
  shows ten distinct, plausible master plans without waiting on real client exports.
  The loader already branches on `plan.asset.url`, so dropping in a real `.glb` per
  project is a one-line data change.
- **Shared GL context** (three.js renders into MapLibre's canvas) rather than a second
  overlaid canvas - keeps depth and camera consistent, and costs one context.
- **Simulated network latency** (`SIMULATE_NETWORK` in `js/streaming.js`) so the
  streaming is visible in a demo. Turn it off to measure real speed.

## Known gaps / next after prototype

- Real geometry pipeline: Unreal -> glTF/Draco -> 3D Tiles per project, on a CDN.
- Interiors: keep them in the Unreal build and deep-link, or pixel-stream on demand.
- Auth + per-client admin to upload models and edit project copy.
- Analytics: which projects get viewed, how long, from where.
- Real site placement (surveyed origin, rotation, site polygon) instead of a generated
  footprint around the pin.
- Shadows are enabled but subtle at these light levels; worth a pass if the boss wants
  more drama in the hero shot.
- Mobile GPU budget untested on mid-range Android; dials are `LOD.maxResidentModels`
  and `LOD.memoryBudgetMB`.
